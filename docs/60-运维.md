## 2. 部署

```bash
./deploy-home-server.sh           # 全流程
./deploy-home-server.sh sync      # 只 rsync
./deploy-home-server.sh status    # 容器状态
./deploy-home-server.sh logs      # 跟日志
```

全流程五步。步 1–4 任一失败即中止（`set -e`），容器未动、线上保持旧版本；第 5 步 `up -d` 后容器已切换，`wait_healthy` 超时只是脚本报错退出，`/health` 内容异常仅告警不中止；最后跑 `docker image prune -f`。

1. `sync_source`：`rsync -ai --delete` 源码 → `/opt/allin-one`，打印变更清单。
2. `pick_registry`：依次探测 `docker.1ms.run/`、`docker.m.daocloud.io/`、Docker Hub 直连，拉三个基础镜像（`node:22-alpine`、`docker:cli`、`python:3.11-slim`）全部在 `PULL_TIMEOUT`（120s）内成功的第一个即采用；`REGISTRY=` 指定则跳过探测。
3. `build_image`：构建 `allin-one:home-server`（前端 Vite 产物打进镜像）。
4. `run_migrations`：用**新镜像**起一次性容器跑 `alembic upgrade head`，失败则中止，容器未切换。因此迁移必须对旧代码向后兼容（加表 / 加列 / 加索引），破坏性变更拆两次发布。
5. `up -d` 后 `wait_healthy` 等容器 healthy（45 × 2s），再 `curl $HEALTH_URL`（默认 `http://192.168.1.103:8000/health`），最后打印镜像内前端入口文件名（`/app/static/assets/index-*.js`）供人工比对，脚本不做自动一致性校验。

**回滚**：脚本不打标，人工约定部署前 `docker tag allin-one:home-server allin-one:backup-<date>`（脚本结尾的 `docker image prune -f` 会清掉未打标的旧镜像）；回滚 = retag 回来 + `docker compose -f /opt/allin-one/docker-compose.home-server.yml up -d`。数据库迁移不回滚（脚本无 downgrade 路径）。

**全新环境初始化顺序**：起 Postgres → `alembic upgrade head` → 起应用与 worker。应用启动调 `init_db()` → `Base.metadata.create_all`，若先起应用会先建表、之后 alembic 报 DuplicateTable（处置 `alembic stamp` 来自 memory 记载，未在主机复现）。

**漂移**：memory 记载生产目录曾被直接修改未回流（事件本身无主机证据）。部署前 `diff -rq /root/workspace/the-one/allin-one/backend /opt/allin-one/backend`。the-one `/health-check` 的部署漂移项只比 `~/.local/bin` 与 the-one `scripts/`，不覆盖 `/opt/allin-one`。

## 3. 运行

**容器**（`docker compose -f /opt/allin-one/docker-compose.home-server.yml <cmd>`，全部 `restart: unless-stopped`，日志轮转 10MB × 3）：

| 容器 | 职责 | 健康检查 |
|---|---|---|
| `allin-one` | FastAPI + 静态前端，:8000 | 30s 一次 `GET /health`，start_period 40s |
| `allin-worker-pipeline` | Procrastinate worker，`pipeline` 队列，并发 4 | `SELECT 1` |
| `allin-worker-scheduled` | Procrastinate worker，`scheduled` 队列，并发 2；periodic 任务在这里触发 | `SELECT 1` |
| `allin-mcp` | MCP HTTP，:8001，只挂 `.env` | — |
| `allin-postgres` | PostgreSQL 17，`TZ=UTC`，库 / 应用用户 `allinone`（`init-databases.sql` 建）；容器超级用户 `postgres` | — |
| `allin-rsshub` | 非标准平台 feed 生成 | — |
| `allin-browserless` | 无头 Chromium，供 RSSHub puppeteer 路由与 L3 抓取 | — |

单个容器重启：`docker compose -f … restart allin-worker-scheduled`。改了代码不能只 restart，代码在镜像里，要走部署。

**periodic 任务**（`backend/app/tasks/scheduled_tasks.py`，cron 为 UTC，由 scheduled worker 触发）：

| 任务 | cron | 说明 |
|---|---|---|
| `check_and_collect_sources` | 每 1 分钟 | 选 `is_active AND schedule_enabled AND (next_collection_at <= now OR IS NULL)` 且可调度的源入队采集；同一任务还做孤儿内容补偿与卡死步骤恢复 |
| `auto_sync_sources` | 每 10 分钟 | 按注册表 `auto_sync_minutes` 到期发起内置同步（目前只有 Emby，30 分钟） |
| `cleanup_scheduler` | 每小时 | 到 `cleanup_content_time`（03:00 UTC = 11:00 CST，±30 分钟窗）跑内容清理，到 `cleanup_records_time`（03:30 UTC）跑记录清理（含 7 天前的 `sync_task_progress`）；上次内容清理 2026-09-23 |
| `analyze_source_periodicity` | 20:00 UTC（04:00 CST） | 采集型源的发布周期分析 |
| `cleanup_job_queue` | 19:20 UTC（03:20 CST） | 删 7 天前结束的作业，回收心跳丢失超 1 小时的僵死作业 |
| `trigger_daily_report` / `trigger_weekly_report` | 已注释停用（2026-09-20） | 列入 `system_health._RETIRED_TASKS`，历史失败不计入总评 |

**保留参数**（系统设置 → 内容保留 tab，存 `system_settings`）：默认保留天数 `default_retention_days` 未存值，按代码默认 30 天生效，`source_configs.retention_days` 可按源覆盖（69 个源均未设；NULL 或 0 都回退全局默认，按源不能设永久）；采集记录保留 90 天、每源至少留 10 条；执行记录保留 `execution_retention_days` 未存值，默认 30 天；调度间隔 300s–86400s。到期按 `collected_at < now − retention` 判定（不是发布时间）；保护条件为已收藏、`user_note` 非空、任一媒体项已收藏；`source.auto_cleanup_enabled` 字段不参与判定；全局值为 0 时整个清理跳过。截至 2026-09-24 最早条目 `collected_at` 为 8-30，尚无内容到期，清理任务未删过任何内容。

**systemd**：`allin-one-backup.timer`（每日 03:30）已安装、**disabled**；无其他单元。

## 4. 数据库

- 连接：容器内 `DATABASE_URL` 指向 `postgres` 服务（compose 四处内联）；连接池按容器在 compose 里设：allin-one 10/5、worker-pipeline 6/4、worker-scheduled 4/2、allin-mcp 3/2（代码默认 10/5）。
- 迁移：`alembic upgrade head`，当前 head `0028_film_countries_iso`；生成 `alembic revision --autogenerate -m …` 后跑 `scripts/verify/drift/check.sh --write` 刷新 `system_design.md` 表结构段。
- 直连：`docker exec allin-postgres psql -U allinone -d allinone`。
- 在生产库上验证改动：`pg_dump` 快照 → 临时 `postgres:17-alpine` 容器（2026-09-23 演练观测：initdb 后容器重启一次，`pg_isready` 提前返回真，要等日志第二次 "ready to accept connections"）→ 用 `allin-one:home-server` 镜像挂载工作区跑 alembic / uvicorn / 脚本；镜像里没有 curl，从宿主机按容器 IP 访问。
- 时间：应用表 naive UTC（`app.core.time.utcnow`）；procrastinate 表是 timestamptz，`system_health.py` 里 `_aware` / `_naive_utc` 换算，别处一律 naive UTC。

```bash
scripts/backup-home-server.sh snapshots

```

| 项 | 值 |
|---|---|

## 6. 日志与监控

**日志**：

| 位置 | 内容 |
|---|---|
| `docker logs <容器>` | 各容器 stdout，10MB × 3 轮转 |
| `/opt/allin-one/data/logs/backend.log` | API 进程，`RotatingFileHandler` 10MB × 5，只收 WARNING 及以上 |
| `/opt/allin-one/data/logs/worker.log` | worker 进程，同上 |
| `/opt/allin-one/data/logs/error.log` | 所有进程的 ERROR 汇总 |
| `LOG_LEVEL` | compose `environment` 注入（allin-one 与两 worker 为 INFO；allin-mcp 未设，走代码默认 INFO），只控制控制台输出 |

坑：服务层或 MCP 导入 `app.tasks.procrastinate_app` 会执行 `setup_logging("worker")`，让 API / MCP 进程去写 `worker.log`；`system_health.py` 为此不导入它。

**健康判定**：

| 层 | 方式 |
|---|---|
| 进程 | `GET /health`：`status` 由 database / RSSHub / Browserless 三项决定，另附 `queue_depth`、`disk`；`degraded` 也返回 HTTP 200，compose healthcheck 只看 200，容器 healthy 不代表三项全 ok |
| 系统总评 | MCP `get_system_health(time_range)`：采集、同步、作业、源健康一次拿到，与仪表盘同口径；`get_source_health(problems_only / source_name)` 看单源最近运行与错误文本；`get_recent_failures` |
| 页面 | 仪表盘"信息源健康"三级堆叠条、7 天失败率、需要关注 / 失败排行 |
| 源是否在采集 | `is_active AND schedule_enabled` 两个字段的与，排查必须同时看 |
| the-one `/health-check` | 脚本层：MCP 连接（`claude mcp list`）、部署 vs repo 漂移、digest 水位线年龄；Claude 层：`get_system_health` 转述、关键源白名单时效（`intel/信息源.md` Tier 1）。**未覆盖**：本系统备份心跳 `last-success` |
